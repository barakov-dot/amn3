# Техническое задание

## 1. Назначение

Система должна автоматизировать выдачу и управление VPN-доступами AmneziaWG 2.0 на собственном VPS через Telegram-бота.

На первом этапе поддерживается один VPS. Архитектура должна быть расширяемой до нескольких серверов с ручным выбором локации или автоматическим переключением при недоступности основного сервера.

## 2. Источники и технические ограничения

AmneziaWG 2.0 отличается от классического WireGuard и старых версий AmneziaWG:

- поддерживается в AmneziaVPN 4.8.12.9 и новее;
- для AmneziaWG 2.0 нужны новые конфиги/ключи, конфиги Legacy не обновляются напрямую;
- добавлены параметры `S3` и `S4`;
- параметры `H1-H4` поддерживают диапазоны, которые не должны пересекаться;
- используются `I1-I5`;
- параметры `j1-j3` и `itime` больше не используются.

Официальные опорные материалы:

- https://amneziavpn.org/documentation/instructions/new-amneziawg-selfhosted/
- https://amneziavpn.org/documentation/amnezia-wg/
- https://amneziavpn.org/documentation/supported-linux-os-for-vps/
- https://github.com/amnezia-vpn/amneziawg-go
- https://github.com/amnezia-vpn/amneziawg-linux-kernel-module

## 3. Роли

### Администратор

Может:

- запускать установку/проверку VPS;
- просматривать пользователей;
- создавать конфиги вручную;
- подтверждать заявки;
- выдавать произвольный срок доступа;
- продлевать и отзывать доступ;
- просматривать состояние сервера;
- управлять тарифами/сроками;
- добавлять будущие серверы.

### Пользователь

Может:

- отправить заявку;
- оплатить доступ или ждать ручного подтверждения;
- получить конфиг;
- посмотреть срок действия;
- запросить повторную отправку конфига;
- продлить доступ;
- получить инструкцию по подключению.

Ограничение MVP: не более 5 активных устройств на одного пользователя.

## 4. Сроки доступа

Система должна поддерживать фиксированные периоды:

- 3 дня;
- 7 дней;
- 10 дней;
- 14 дней;
- 30 дней;
- 60 дней;
- 90 дней;
- 180 дней.

Также нужен произвольный срок, задаваемый администратором в днях или датой окончания.

Тестовый срок по умолчанию: 7 дней.

## 5. Telegram-бот

### Пользовательские команды

- `/start` - регистрация и главное меню;
- `Получить доступ` - старт заявки или оплаты;
- `Мой VPN` - статус доступа;
- `Получить конфиг повторно` - повторная выдача файлов;
- `Продлить` - продление доступа;
- `Помощь` - краткие инструкции.

### Административные команды

- `/admin` - админ-панель;
- `/users` - список пользователей;
- `/approve <user_id> <days>` - подтвердить доступ;
- `/revoke <user_id>` - отозвать доступ;
- `/extend <user_id> <days>` - продлить доступ;
- `/server_status` - состояние VPS и AmneziaWG;
- `/plans` - управление сроками/тарифами.

Финальный интерфейс лучше делать через inline-кнопки, а команды оставить как быстрый fallback.

## 6. Оплата и проверка

MVP должен поддерживать два режима:

1. Бесплатный тестовый режим с ручной проверкой: пользователь отправляет заявку, администратор подтверждает, оплата не требуется.
2. Заглушка оплаты: бот фиксирует выбранный тариф и переводит заявку в статус `payment_pending`.

После MVP можно подключить:

- YooKassa;
- CryptoBot;
- Telegram Stars;
- ручную проверку банковского перевода;
- другую платежную систему.

Платежный слой должен быть отдельным модулем, чтобы не переписывать бота при смене провайдера.

## 7. Генерация конфигов

Для каждого пользователя создается отдельный peer:

- private key;
- public key;
- preshared key, если выбран режим с PSK;
- VPN IP из выделенного пула;
- allowed IPs;
- DNS;
- endpoint;
- persistent keepalive;
- AmneziaWG 2.0 параметры `I1-I5`, `S1-S4`, `Jc`, `Jmin`, `Jmax`, `H1-H4`.

Пользователь и администратор должны иметь возможность выбрать версию формата конфига:

- `amneziawg_v1_5`;
- `amneziawg_v2`.

Выбранная версия сохраняется в устройстве и используется при повторной выдаче конфига.

Клиентские настройки MVP:

- DNS: `1.1.1.1`;
- full tunnel: `AllowedIPs = 0.0.0.0/0`.

Генератор должен быть отдельным модулем с версией формата, например `amneziawg_v2`, чтобы при изменениях протокола можно было добавить новый генератор без поломки старых конфигов.

## 8. Выдаваемые форматы

Бот должен выдавать:

- `.conf` файл;
- QR-код;
- текстовую копию конфига по запросу;
- импортируемую ссылку/ключ, если выбранный формат будет подтвержден совместимостью с клиентами AmneziaVPN.

QR-код генерируется из полного содержимого `.conf`.

## 9. Provisioning VPS

Скрипт первичного разворачивания должен:

- работать в non-interactive режиме из заранее заполненного `servers.yml`;
- работать в interactive режиме, если конфиг отсутствует или содержит незаполненные значения;
- спрашивать недостающие данные VPS и генерировать/обновлять `servers.yml`;
- проверить ОС и kernel;
- поддерживать Debian как первый целевой дистрибутив;
- установить зависимости;
- установить AmneziaWG;
- сгенерировать UDP-порт больше `30000`, если порт не задан вручную;
- открыть выбранный UDP-порт в `ufw`;
- включить forwarding;
- настроить firewall/NAT;
- создать серверный keypair;
- создать базовый интерфейс;
- проверить запуск сервиса;
- сохранить server metadata в БД/конфиг проекта.

Для Ubuntu/Debian основной путь установки: официальный PPA/пакеты AmneziaWG или сборка/установка из официальных репозиториев, если пакет недоступен.

Основной runtime для MVP: установка AmneziaWG на хост Debian без Docker, управление через `systemd` и `awg`/`awg-quick`. Это позволяет добавлять и отзывать peer на работающем интерфейсе без постоянного перезапуска Docker-контейнера. Docker может быть добавлен позже как альтернативный backend, если будет выбран контейнерный способ эксплуатации.

## 10. Хранилище

Минимальные сущности:

- `users`;
- `servers`;
- `peers`;
- `plans`;
- `orders`;
- `payments`;
- `admin_actions`;
- `server_health_checks`.

Для MVP можно использовать SQLite. Для продакшна предпочтителен PostgreSQL.

Подробная модель данных MVP описана в [DATA_MODEL.md](DATA_MODEL.md). Ключевое решение: один Telegram-пользователь может иметь несколько устройств, а каждое устройство получает отдельный peer, отдельный VPN IP, отдельные ключи и отдельный срок действия.

## 11. Автоматические задачи

Нужны фоновые задачи:

- отключать истекшие peer;
- предупреждать пользователей перед окончанием срока за 7, 5, 3 и 1 день;
- проверять доступность VPS;
- делать backup базы и серверных конфигов;
- собирать health/status сервера.
- собирать статистику трафика peer и показывать ее пользователю и администратору.

## 12. Безопасность

Обязательные меры:

- Telegram admin allowlist;
- хранение секретов только в `.env` или secret storage;
- не логировать private keys и полные конфиги;
- ограничить SSH-ключ provisioning-пользователя;
- делать backup перед изменением серверного конфига;
- использовать idempotent deploy-скрипты;
- валидировать сроки и Telegram ID;
- rate limit на пользовательские действия.

## 13. Мультисерверность

На первом этапе один сервер. Архитектурно заложить:

- таблицу `servers`;
- статус сервера `active`, `degraded`, `disabled`;
- pool IP на сервер, по умолчанию `10.8.0.0/24`;
- capacity limit;
- selection strategy: manual, least_loaded, failover.

Автоматическая смена сервера при недоступности не означает мгновенный перенос существующего туннеля. Реалистичная стратегия: выдать новый конфиг на резервном сервере и пометить старый peer как проблемный.

Все серверы должны управляться из одного Telegram-бота. Для роста выше 255 устройств на одном сервере нужно либо расширять пул до более крупной сети, например `/16`, либо добавлять новые серверы с отдельными пулами.

## 14. MVP

MVP считается готовым, если:

- бот запускается локально;
- админ может зарегистрировать VPS;
- provisioning разворачивает AmneziaWG 2.0;
- админ может выдать пользователю доступ на выбранный срок;
- пользователь получает `.conf` и QR;
- просроченный доступ автоматически отключается;
- есть базовые логи и backup.
