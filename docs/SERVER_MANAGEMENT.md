# Управление VPN-серверами

## Общая идея

Telegram-бот работает отдельно от VPN-серверов и управляет ими централизованно.

Для каждого VPN-сервера бот хранит:

- SSH host/port;
- endpoint для клиентов;
- VPN UDP-порт;
- VPN address pool;
- runtime;
- статус доступности;
- количество активных устройств.

На первом этапе сервер один. В будущем серверов может быть несколько, но интерфейс управления остается один: Telegram-бот.

Подключение нового сервера должно быть возможно двумя способами:

- через заранее заполненный `servers.yml`;
- через интерактивный мастер, который спрашивает данные VPS и создает/обновляет `servers.yml`.

## Runtime

Основной runtime для MVP:

- Debian VPS;
- AmneziaWG 2.0 установлен на хост;
- управление через `systemd`;
- интерфейс поднимается через `awg-quick`;
- peer применяются через `awg`.

Такой подход позволяет:

- не зависеть от постоянно перезапускаемого Docker-контейнера;
- добавлять peer без остановки VPN-интерфейса;
- отзывать peer без пересоздания контейнера;
- сохранять итоговое состояние в серверный конфиг после успешного применения.

Docker можно добавить позже как альтернативный backend. В этом случае нужен отдельный `server_manager`, который умеет безопасно менять peer внутри контейнерного окружения.

## Добавление peer

Рекомендуемый порядок:

1. Создать запись `device` в БД со статусом `pending`.
2. Выделить свободный IP из пула сервера.
3. Сгенерировать ключи.
4. Сформировать peer.
5. Применить peer на работающем интерфейсе через `awg`.
6. Сохранить peer в постоянный серверный конфиг.
7. Сделать backup измененного конфига.
8. Перевести устройство в статус `active`.
9. Отправить пользователю `.conf`, QR и ссылку/ключ, если формат подтвержден.

Если шаг применения на сервере не прошел, запись остается `pending` или переводится в `failed`, а IP освобождается.

## Отзыв peer

Рекомендуемый порядок:

1. Найти устройство пользователя.
2. Удалить peer из работающего интерфейса.
3. Удалить или закомментировать peer в постоянном серверном конфиге.
4. Сделать backup.
5. Обновить статус устройства: `revoked` или `expired`.
6. Сохранить причину отзыва.

## Порты

Если порт не задан администратором:

- сгенерировать случайный UDP-порт из диапазона `30001-65535`;
- проверить, что он не используется на сервере;
- открыть порт в `ufw`;
- сохранить порт в `servers.vpn_port`;
- использовать его в endpoint пользовательских конфигов.

## Адресные пулы

Базовый пул первого сервера: `10.8.0.0/24`.

Такого пула хватает примерно на 253-254 клиентских IP, если исключить адрес сети, broadcast и адрес сервера. Если устройств будет больше, есть два пути:

- расширить пул, например до `10.8.0.0/16`;
- добавить новые серверы с отдельными пулами, например `10.9.0.0/24`, `10.10.0.0/24`.

В коде нужен IPAM-слой, который:

- знает CIDR каждого сервера;
- не выдает занятые IP;
- не выдает служебный IP сервера;
- умеет расширяться на несколько серверов;
- блокирует race condition при одновременной выдаче нескольких конфигов.

## Мультисерверность

Все серверы управляются из одного бота.

Стратегии выбора сервера:

- `manual` - администратор или пользователь выбирает сервер;
- `least_loaded` - система выбирает сервер с меньшим числом активных устройств;
- `failover` - при недоступности основного сервера выпускается новый конфиг на резервном сервере.

Важно: failover не переносит активный туннель мгновенно. Пользователь получает новый конфиг на другом сервере.

## Health check

Для каждого сервера нужно проверять:

- SSH доступность;
- активность systemd-сервиса;
- состояние интерфейса;
- открыт ли UDP-порт;
- количество peer;
- свободные IP в пуле;
- доступное место на диске.
