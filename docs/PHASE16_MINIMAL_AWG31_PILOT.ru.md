- Без аргументов / `plan`: только несекретный JSON-план, без внешних команд и записи файлов.
- `check`: read-only проверка Ubuntu 24.04, amd64, root, dedicated Docker, TUN, forwarding, адреса сервера, свободных ресурсов и снимка AWG2. Ключи и конфиги не требуются.
- `render --key-directory PATH --dns ADDRESS --mtu 1280`: создание ровно двух защищённых файлов — серверного и одного Windows-клиентского. Требует отдельного разрешения; работает только на Linux.
- `check --with-profiles`: дополнительно проверяет пару конфигов и возвращает их хеши.
- `apply`: требует `--script-sha256`, `--state-sha256`, `--server-sha256`, `--client-sha256`, `--claim`. Повторно проверяет состояние, сохраняет одноразовую запись попытки и защищённый снимок входных файлов, проверяет конфиги штатным AWG и запускает один runtime.

Ключи для `render` должны быть заранее созданы штатными `awg genkey`, `awg pubkey`, `awg genpsk` в отдельно разрешённом шаге. Имена защищённых входных файлов: `server_private.key`, `server_public.key`, `client_private.key`, `client_public.key`, `psk.key`, `hpk.key`. Секреты не передаются в аргументах, не печатаются и не включаются в Git. `render` не генерирует ключи и не перезаписывает существующий каталог.

## Изоляция и ограничения

Используется закреплённый образ `amneziavpn/amneziawg-go` с digest `4e1fd2840f8d26eb6ec8bc1598e66f2f17f5d0201cd2baadbde560c104d4fc9d`. Контейнер `amn2-spain-awg31-pilot`, сеть `amn2sp31pilot`, UDP 30002, VPN `10.212.13.0/24`; прежние приложение, SQLite, Telegram и SSH-bootstrap не используются.

Проверка реальным `awg`/`awg-quick` и сверка private/public выполняются в контейнере `--network none`, до создания постоянной сети и публикации порта. Runtime явно userspace; клиентский приватный ключ в рабочий контейнер не монтируется. Сравнение AWG2 использует наблюдавшиеся `amn2-spain-awg` / `awgsp0`, без требования клиентского трафика. Старый freshness-контракт package 016 не изменён.

На ошибке удаляются только ресурсы данной попытки, по ID или уникальной метке; неуспешный откат помечается `failed_or_unknown`. Образ остаётся в кэше; входные конфиги, их защищённый снимок и журнал сохраняются. Это не полный возврат файловой системы к прежнему состоянию. Нет автоматического повтора, удаления AWG2 или общей выдачи.

Это IPv4-пилот. `::/0` направляется клиентом в туннель, но сервер IPv6 не маршрутизирует; отсутствие утечек требует клиентского теста. MTU 1280 — начальная настройка пилота, не диагноз медленного AWG2. Автоматический перезапуск отключён. Успех запуска означает только `pilot_started_client_test_pending`, не acceptance.

Временное сетевое дополнение: `scripts/vps/phase16_awg31_pilot_firewall.py` формирует одну собственную NAT-таблицу `ip amn2_p16_awg31` и три адресно-интерфейсных правила в существующем `ip filter FORWARD`. Оно не очищает ruleset, не меняет политики цепочек и не отключает UFW. Перед применением обязательны native-check, сверка состояния и bindings существующего пилота; при ошибке проверки удаляются только добавленные ресурсы. Модуль сам по себе не запускает SSH. Будущая постоянная интеграция и автоматический запуск остаются отдельной задачей после успешного теста.

Первоначальная подготовка требовала отдельных разрешений на передачу файла, подготовку секретов и применение одного профиля; фактически полученные разрешения и результаты перечислены выше. Старые package approval/transaction не переиспользуются. Текущее разрешение на достижение первого теста не распространяется на общую выдачу, изменение AWG2 или публичную публикацию истории. `check` не заменяет проверку firewall-пути и клиентской версии; скрипт проверяет bindings, но сам не выдаёт операторское разрешение.
