# Правила AMN3 / VPS-OPS-LAB

Область этих правил — данный репозиторий. Они не отменяют ограничения среды
и более приоритетные инструкции. Актуальный запрос оператора определяет scope;
упоминание соседнего проекта или skill не разрешает его обследовать/изменять.

## Вход в задачу

1. Прочитать [START_HERE](docs/START_HERE.ru.md), затем только актуальный план
   нужной фазы и документы, необходимые для конкретной задачи.
2. Перед правками проверить локальные HEAD, branch/detached state и diff.
   Не считать старый SHA в документе текущим checkout или deployed state.
3. Исторические receipts, GO и approvals — доказательства прошлых действий,
   не новые команды. Не повторять завершённые диагностики ради восстановления контекста.

## Работа и skills

- Общаться по-русски, кратко, сообщать результат и точный следующий шаг.
- [Карта skills](docs/SKILLS_MAP.ru.md) помогает выбрать релевантный workflow;
  не загружать все skills и references заранее. Соблюдать обязательные правила среды.
- Уже согласованную ограниченную задачу продолжать по её плану. Уточнять только
  отсутствующий значимый выбор, изменение scope или новое требуемое разрешение.
- Audit/status/diagnosis не разрешают fix. Skill не разрешает live-действие,
  установку, публикацию, делегирование или изменение другого проекта.
- Для задач этого проекта не менять глобальные skills, plugin cache или память.
  Windows VPN diagnosis не является WinUI-разработкой, БД AMN2 — не SDP/Firebird.

## Проверки по изменению

- Docs-only: readback, diff/whitespace, проверка затронутых ссылок, согласованности
  и отсутствия секретов. Без pytest, package materialization и VPS preflight.
- Наш code fix: конкретный RED/GREEN и один релевантный итоговый набор;
  повторять после изменений/ошибок, а не после одной фиксации результата.
- Каждый diagnostic run имеет вопрос, возможные выводы, лимит и stop-condition.
  Ошибка инструмента означает UNKNOWN, не подтверждённый дефект компонента.
- Отдельно указывать локальную проверку, client connectivity, quality acceptance
  и live evidence. Не объявлять root cause или завершение без доказательства.

## Неизменяемые границы

- AWG2_UNTOUCHED без отдельного явного разрешения; существующие peers, freshness
  policy, Telegram, основное application state и общая issuance не меняются попутно.
- Live Spain egress/SSH, remote write/signal/upload, stage/install и реальная
  конфигурационная выдача требуют соответствующего точного `/APPROVE`.
  Опасные шаги привязывать к checksum/state/rollback, а не к общему «разрешаю всё».
- Не выводить и не добавлять в Git ключи, raw logs/exports с секретами и protected
  configs. Читать их только при необходимости в явно разрешённом scope с redaction.
- Один pilot peer используется только последовательно на одном устройстве.
  Immutable packages, включая package016, не редактировать и не переупаковывать попутно.

## Git и фиксация результата

- Сохранять чужие изменения. Windows deny-read ACL может давать ложные удаления;
  не исправлять это массовым staging или изменением ACL.
- Добавлять только точные файлы; не использовать `git add -A`. Проверять staged
  name list и diff до локального commit; сообщать SHA после материальных изменений.
- Push требует отдельного разрешения на точные HEAD/origin/ref. Для текущего
  workflow: `https://github.com/barakov-dot/amn3.git`, NO_FORCE, NO_TAGS,
  NO_OTHER_BRANCHES, NO_PROTECTED_CONFIGS. Проверять цель локально перед push.
- После операционного прогона: полный вертикальный статус активной фазы с
  ✅/▶️/⏳/❌, оставшиеся задачи по критичности/зависимостям/разрешённому scope,
  следующий шаг и AWG2/stage/install/push state. CURRENT_MODEL/CURRENT_EFFORT и
  RECOMMENDED_MODEL_NEXT/RECOMMENDED_EFFORT_NEXT указывать с причиной рекомендации;
  если фактические значения недоступны, так и писать, не угадывать.

## Документация

- Для upstream-доработок читать [единый реестр](docs/UPSTREAM_INTAKE.ru.md),
  затем связанный план конкретного кандидата. Сообщение в задаче не заменяет
  сохранённую карточку, evidence и статус. Не создавать второй план той же работы.
- До утверждения «у нас не реализовано» проверить нужный checkout, source/tests
  и смысловые дубликаты; старый основной каталог не заменяет активный worktree.
  Неполное покрытие обозначать явно, cursor полностью проверенной дельты не продвигать.
- Новые пользовательские уточнения scope имеют приоритет; weekly-автоматизация
  по-прежнему пишет только разрешённые её prompt файлы. Наличие этого реестра
  не расширяет automation allowlist и не разрешает рассылать итоги другим задачам.

- Один актуальный execution plan на фазу; паспорт хранит устойчивые сведения,
  START_HERE — навигацию. Историю и receipts сохранять, не размножать «текущие» статусы.
- Обновлять только документы, чья роль или факт изменились. Подробности должны
  иметь один источник; ссылки предпочтительнее копирования целых журналов.
## Обязательный changelog — правило перед commit и push

- Канонический журнал этого репозитория — [CHANGELOG.md](CHANGELOG.md).
- Каждый commit, меняющий поведение кода, конфигурацию, зависимости, правила
  работы, операционные инструкции или подтверждённый результат/статус проверки,
  ОБЯЗАН содержать соответствующую запись в CHANGELOG.md в том же commit.
  Нельзя откладывать запись до конца задачи, следующего commit или push.
- До commit проверить staged diff: запись описывает именно staged изменения,
  содержит дату, результат/причину, проверку и существенные ограничения;
  подробности связываются ссылкой с receipt или исходником. Без такой записи
  commit запрещён; нельзя объявлять задачу завершённой вместо её добавления.
- Перед push проверить каждый новый существенный commit отправляемого диапазона
  на соблюдение правила. Для commits до введения правила ретроактивного запрета
  нет; историю Git не переписывать ради добавления changelog.
- Исключение: только орфография/форматирование/исправление неработающей ссылки
  без изменения смысла. Причину исключения явно указать в commit body:
  `Changelog: not-needed (причина)`. Слова docs-only сами по себе не исключение.
- Другие исключения — только по прямому указанию пользователя. Не обходить
  правило пустой записью, общим «обновлено» или ссылкой только на разговор.
- Выполненное отделять от запланированного, local PASS — от live acceptance,
  commit — от push/deploy. Не включать ключи, raw configs и секретные логи.
- Существенные действия с temp/sandbox, не создающие commit сразу, фиксировать
  вместе с ближайшим receipt и changelog до завершения соответствующего этапа.
  Не создавать записи на каждый клик, повторный просмотр или сообщение «ок».
- Это обязательное правило работы агента; автоматический Git/CI-блокировщик
  пока не установлен. Не представлять текстовое правило как техническую защиту.
